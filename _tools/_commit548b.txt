548: reporting — hourly file-to-email status report

The operator gets one periodic snapshot of this symbol's state each hour, on top
of the per-trade exit email the journal already ships. Until now the only
asynchronous signal from a running chart was the exit mail, so a position the EA
was quietly trailing -- or an hour in which it placed nothing -- was invisible
without opening the terminal.

The report follows ONE contract, and it is the journal's:

  * a FLAT text file is WRITTEN, CLOSED, and then RE-OPENED and mailed, so the
    artifact on disk and the body of the email are the same bytes;
  * line 0 is the subject, in the same "SUBJECT: ..." shape the per-session
    journal uses, so a single file is simultaneously a readable log and a
    message;
  * SendMail() is suppressed inside the Strategy Tester, which cannot dispatch
    mail, but the FILE is still written -- a tester run leaves the same evidence
    a live run does;
  * the file is NOT deleted afterwards. The leftover _HourlyReport.txt IS the
    audit trail the operator asked for.

Mechanics:

  1. A GATE, NOT A TIMER. EmitHourlyStatusReportIfDue() compares
     TimeCurrent() against m_lastHourlyReport and fires once the delta reaches
     #define OTTO_HOURLY_REPORT_SECONDS (3600). TimeCurrent() and not
     TimeLocal(): the local clock reads the operator's time zone, which is the
     wrong wall time on a VPS and silently different on a weekend. The stamp is
     advanced BEFORE the send, so a refused mail or a failed write costs an
     hour, not a per-tick mail storm. The stamp is zeroed by the constructor and
     armed in Initialize(), so a re-init starts a fresh hour instead of
     inheriting a stale one -- the same discipline m_manualNoSLWarnTick follows.

  2. WIRED IN FIRST. Update() calls the gate as its first statement, ahead of
     CompleteReversal() and the two fill scans, so the report describes the book
     as the tick found it rather than mid-mutation. On the ticks that are not
     due the cost is one subtraction.

  3. WHAT IT REPORTS. [BOOK] the live basket (ticket, side, entry, working stop,
     1R, adopted-manual flag), the hybrid pending count, and the armed-setup
     count; [COUNTERS] placed / filled / rejected / stop-failures / reversals /
     retries since init; [RISK] equity, balance, floating P/L and free margin;
     [MARKET] bid, ask, spread in points and ATR. Every field is a live read at
     the moment of the report; nothing is cached between hours.

  4. CountArmedBlocks(). The "how many live setups do I have" number, which the
     pending count alone cannot answer: a virtual order is armed before it ever
     produces a broker row, and a physical one keeps a row that already exists.
     A block counts when it is armed and not vetoed, triggered or exited.

WHY THIS DOES NOT GO THROUGH COttoJournal

SendMailFromFile() in COttoJournal is pinned to exactly ONE call site (LogExit)
by test_v542_email.py and test_v545_throttle.py -- that pin is what encodes the
one-email-per-trade rule and the removal of cancellation spam. Routing the
hourly report through the journal would have added a second call site and broken
both probes, and with them the guarantee they encode. So the hourly report owns
its own file and its own native SendMail() call, MQL_TESTER-guarded in the same
shape CHighTableAuditor::DispatchAlert() uses. COttoJournal.mqh is untouched.

Recorded, not altered: InitiateReversal() remains unreachable (no caller
anywhere) and CompleteReversal() still early-returns unless m_reversalInProgress
is set, which only InitiateReversal() does -- that pair is dead code, restated
from 548a. The live reversal is the SAR branch plus the direction resolver.
Deleting dead code is its own change, not a drive-by in a reporting commit.
