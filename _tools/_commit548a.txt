548: execution — seed the virtual fill from its own side, not the block's new phase

Phase 2 of a block's lifecycle is an S/R FLIP, and GetDirectionForBlock() is the
one place that decides which side a block is on: touches == 0 is the Phase 1
"N"ormal bounce, touches >= 1 is the Phase 2 "R"eversal, where support trades
SHORT and resistance trades LONG. That single resolver feeds the entry, the SL,
the TP, the basket seed and the correlation gate at once.

SeedActiveTradeFromBlock() historically derived the live basket's direction from
that resolver -- correct only while the block is still in the phase that was just
filled. The two fill paths disagree about WHEN they consume the touch:

  * CheckPendingOrderFills() (PHYSICAL resting limit) SEEDS FIRST, then runs
    mod.touches += 1. At seed time the block is still Phase 1, so the derived
    direction equals the side of the resting limit the broker just filled. This
    path was, and remains, correct.

  * CheckVirtualTriggers() (VIRTUAL market fire) consumed the touch FIRST
    (block.touches += 1), then seeded. The increment promotes a Phase 1 block to
    touches == 1, so the resolver now reported the FLIPPED side -- while the
    MARKET order that filled a moment earlier had been sent on the arm-time side
    (vo.direction). A Phase 1 fire therefore seeded its basket with the OPPOSITE
    direction to the live position.

The desync was silent and durable: m_activeTrade.direction and m_activeDirection
drive the trail (which way "favourable" is), the 1R basis, the journal entry and
the High Table phantom-mirror for the entire life of that leg. Nothing threw and
no log line showed it.

  1. ONE OPTIONAL OVERRIDE. SeedActiveTradeFromBlock() now takes
     `ENUM_TRADE_DIRECTION overrideDir = DIR_NONE`. A non-DIR_NONE value is used
     verbatim; DIR_NONE keeps the old phase-derived behaviour. The seeding site
     stays a single chokepoint, so a future fill path gets the correct default
     and can opt into an explicit side only when it actually needs one.

  2. THE VIRTUAL PATH CAPTURES ITS OWN SIDE. CheckVirtualTriggers() records
     `ENUM_TRADE_DIRECTION seedDir = isLong ? DIR_LONG : DIR_SHORT;` from
     vo.direction BEFORE it consumes the touch, and passes it to the seed. The
     value describes the order that was actually sent, so the increment can no
     longer reach back and relabel the basket.

  3. THE PHYSICAL PATH IS UNTOUCHED. It still calls the seed with two arguments
     and still seeds before its increment, which is exactly why it never showed
     the defect. Both paths are now pinned in their correct order.

Found while verifying the Phase 2 reversal and virtual-market execution paths for
this release. Recorded, not altered: InitiateReversal() is unreachable (it has no
caller anywhere in the tree) and CompleteReversal() early-returns unless
m_reversalInProgress is set, which only InitiateReversal() does -- so that pair is
dead code. The LIVE reversal is the SAR branch in both fill paths plus this
resolver. InitiateReversal/CompleteReversal/OpenReversalPosition are left exactly
as they are; deleting dead code is a decision for its own change, not a drive-by.
