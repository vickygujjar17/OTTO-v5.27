567: fix — journal printed the SUPPORT stop on the wrong side of its zone

RATIONALE

  No trading geometry changes. The entry remains NEAR edge +/-
  (2.0*blockHeight + 1.5*ATR), the BREAK veto remains anchored on
  BlockEntryPrice(), and slDist remains blockHeight + 0.5*ATR. One printed
  sign moved.

  slDist is IDENTICAL in both directions, so with the far edge pinned at 0.0
  and the near edge one blockHeight inside it:

    LONG  (RESISTANCE): near = -bh, entry = -bh + gap =  bh + 1.5*ATR
                        stop  = entry - slDist      =  +1.0*ATR   ABOVE
    SHORT (SUPPORT)   : near = +bh, entry = +bh - gap = -bh - 1.5*ATR
                        stop  = entry + slDist      =  -1.0*ATR   BELOW

  The blockHeight terms cancel exactly, so the stop always lands one full ATR
  past the far edge and only the SIGN follows the direction. v5.57..v5.66
  printed "SL at Far Edge + 1.0*ATR" for BOTH rows. The RESISTANCE row was
  correct; the SUPPORT row described a stop 1.0*ATR on the wrong side of its
  own zone -- the mirror image of where the broker stop actually sits. An
  operator reading "SL at Far Edge + 1.0*ATR" beside "Zone Top=T | Bottom=B"
  computes a SUPPORT stop ABOVE the block when the code places it BELOW.

  Nothing tied that caption to CalcSLDistance(), which is why it survived four
  releases. v5.58 synced the journal to the anticipation model and pinned the
  entry clauses; the SL half was copied across with the sign unexamined.

CONSIDERED AND REJECTED: INVERTING THE ENTRY SIGNS

  The report this release answers asked for the ENTRY signs to flip:
  b.bottom - gap for LONG, b.top + gap for SHORT. That would be a regression,
  not a fix, and was declined on evidence:

  * git log -S 'block.bottom - gap' returns NOTHING. The requested LONG form
    has never existed in this repository, so it cannot be a restore.
  * e2568aa^ (v5.65) carried `(BlockDirection(b) == DIR_LONG) ? (b.bottom +
    slDist) : (b.top - slDist)` -- the SAME polarity as today. v5.66 widened
    slDist into gap; no sign has ever flipped.
  * `+gap` is the documented design, not a slip: the entry is measured OUT
    from the NEAR edge, which at arm time the breakout has only just cleared,
    so price is still short of it and the trigger is a genuine STOP cross.
    OttoDefines.mqh states the fill lands blockHeight + 1.5*ATR BEYOND the
    far edge, and CheckVirtualTriggers() fires a LONG only when the ask RISES
    to the level (`isLong ? (ask < triggerPrice)`).
  * Under the requested signs breakLevel for a LONG becomes b.bottom - gap,
    which sits BELOW spot. The re-anchored test at ProcessBlocks
    (close1 > breakLevel + ATRBufferBreak*atrNow) is then TRUE on the first
    close after arming: SetVeto(i, VETO_BROKEN) fires and
    CancelOrdersForInvalidBlocks() drops the pending before price can reach
    it. Every LONG dies instantly, mirrored for every SHORT -- reintroducing
    on 100% of blocks exactly the failure e2568aa fixed on a subset.
  * GetOrderTypeForBlock() returns BUY_LIMIT/SELL_LIMIT, so a LONG entry
    below a RESISTANCE zone would rest as a pullback limit, which the v5.52
    pure-continuation mapping deliberately retired.

  A pre-breakout limit entry is a legitimate but DIFFERENT feature. It needs
  its own entry style with inverted break-veto polarity, an inverted cross
  test, and STOP/LIMIT dispatch. It is not a two-line sign change and is out
  of scope here.
