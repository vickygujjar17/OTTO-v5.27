547: order routing — prevent FOK/IOC structural rejections on pending limits

SendOrderWithRetry() in COttoOrderManager.mqh is the EA's single outbound trade
call: pending limit placement, position close, reversal entry, SL/TP modify, the
pyramid tranche and the retry itself all funnel through the ONE OrderSend()
inside it. So the filling mode chosen there is applied to every request the EA
sends -- and the function chose it unconditionally:

    request.type_filling = GetFillingMode();   // dynamic FOK/IOC/RETURN

GetFillingMode() reads SYMBOL_FILLING_MODE, which advertises which fill policies
the symbol's DEALS accept (FOK / IOC). That is the correct question for a MARKET
deal and the wrong one for a resting pending limit, which carries no executable
price at send time. On a strict venue the dynamic FOK/IOC is structurally
invalid there and is rejected with TRADE_RETCODE_INVALID_FILL.

The rejection was SILENT, which is what made it worth a release:

  * TRADE_RETCODE_INVALID_FILL is not in the retry ladder's retry set, so the
    loop did not re-attempt the send;
  * the pending limit was therefore never placed, and the strategy carried no
    order where it believed it had one -- an armed block with no broker row.

  1. ACTION-GATED FILLING. The dynamic mode is now applied only to a
     TRADE_ACTION_DEAL request; every other action takes ORDER_FILLING_RETURN,
     the only filling mode MT5 defines for a pending order. A DEAL keeps the
     dynamic FOK/IOC it needs, so nothing about the market path changes.

  2. NEUTRAL ELSEWHERE. MT5 ignores type_filling on TRADE_ACTION_REMOVE and
     TRADE_ACTION_SLTP, so routing those to RETURN is a no-op today and
     future-proofs any action added later. The guard is placed inside the retry
     loop, matching the v5.37 comment guard beside it, so OrderSend() reads a
     correct mode on every attempt.

Unchanged on purpose: GetFillingMode() itself (still FOK, then IOC, then
RETURN), the retry ladder, the throttle, and every call site. The pyramid path's
own req.type_filling = GetFillingMode() is a DEAL request and stays as-is.


TOOLING

Two latent defects in _tools/_bump_version.py, both exposed by this release's
bump and both fixed:

  * The post-bump staleness census flagged ANY surviving old-release literal,
    including lines carrying a historical 'FIX (vX)' annotation -- the very
    markers the bump pass skips on purpose. A tree that had landed a fix would
    therefore fail its own bump guard. The census now applies the same 'FIX ('
    exemption the bump already did.
  * Re-running the bump with an explicit target equal to the current release
    aborted as an error. It is now a no-op, so a bump-then-verify sequence
    cannot be broken by its own second invocation. The bare (no-argument) form
    still advances one minor, by design.

Three prose comments in CHighTableAuditor.mqh that named v5.46 in the bare
'// v5.46 -' form are restated as 'FIX (v5.46):' so the historical annotation is
in the shape the tooling exempts. Wording only; no code changed.

_probe/test_v546_risk_isolation.py is now release-agnostic. Its stamp check
pinned the literal {5.46} and so failed on any later bump; it now asserts the
invariant that actually matters -- every shipped source carries the SAME stamp.
Two assertions stranded after raise SystemExit(main()) (dead, never executed)
were moved into the live section, which is why that probe now reports 28 checks
where it previously reported 26.
