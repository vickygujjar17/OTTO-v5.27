572: feat — strict limit-only execution: retire the virtual fallback

RATIONALE

  Since v5.37 this EA has carried TWO execution engines. A setup whose
  front-edge entry was legal for a pending order RESTED at the broker
  (ROUTE A, physical). A setup whose price had already run through the entry
  was held in memory as an SVirtualOrder and fired as a TRADE_ACTION_DEAL
  MARKET order the instant price crossed the trigger (ROUTE B, virtual). A
  refused ROUTE A send fell through to ROUTE B as well.

  v5.69 made ROUTE A the ordinary case by moving the entry to the near side of
  the zone. That left ROUTE B as a fallback that could only ever fire in the
  one situation it must not:

      price has ALREADY gapped through the entry.

  The setup's own premise is "fill on the pullback back through the near
  edge". A gap through that level is the state in which the premise is
  invalidated -- and the fallback's response was to buy the far side of the
  move at market and report it as a normal continuation fill. Recording a
  worse entry as if it were the intended one is precisely the failure mode a
  limit order exists to prevent.

  This release removes the engine rather than gating it. There is no input, no
  switch and no "safe mode": an entry is a resting broker limit or it does not
  happen.

WHY THE FALLBACK DID NOT SURVIVE THE GEOMETRY CHANGE

  Before v5.69 the entry sat BEYOND the far edge as a breakout, so "price has
  already passed the entry" was the NORMAL arm-time state and the virtual arm
  was the primary path -- the limit existed for the rare tick that happened to
  reach the level late. v5.69 inverted that: the entry is now 2.0*blockHeight +
  1.5*ATR on the opposite side of the zone, below the market for a LONG and
  above it for a SHORT, which is exactly where a BUY_LIMIT / SELL_LIMIT is
  legal. The physical route therefore carries the ordinary case, and the
  fallback's trigger condition became synonymous with "this setup has already
  failed its own premise".

  A route whose only remaining firing condition is a failed premise is not a
  fallback. It is a mechanism for converting missed trades into worse ones.

WHAT IS REMOVED

    SVirtualOrder, m_virtualOrders[], m_virtualCount
    CheckVirtualTriggers()            and its Update() hook
    VirtualArmGvName()                (v5.49 cross-chart arm lock)
    ReleaseAllVirtualArmLocks()       (ditto)
    RemoveVirtualOrderAt()            and all eight element-removal sites
    the Book-2 half of IsAnyOrderLiveAtPrice()
    the "+ m_virtualCount" term of CountMyPendingOrders()
    the virtual walks in CancelOrdersForInvalidBlocks(),
      CancelOpposingConsensusOrders() and ManageDirectionConflict()
    the virtual-book empties in the constructor, CancelAllPendingOrders()
      and ClearBasket()

  SeedActiveTradeFromBlock() also loses its overrideDir parameter: the MARKET
  fire was its only caller, so the derived direction is the only path left.

  The v5.49 cross-chart arm lock is removed WITH the engine that needed it. A
  virtual arm lived only in the arming instance's memory, so two charts could
  arm the same zone; a GlobalVariable was the shared artefact that stopped
  them. A resting broker limit IS such an artefact -- the duplicate shield
  reads it directly -- so ROUTE A never required the lock. Nothing else read
  the name.

WHY A NEW VETO REASON

  A missed limit is not a broken block. VETO_BROKEN means the ZONE failed:
  price closed back through the physical far edge. A missed limit means the
  zone is intact and the ENTRY could not be placed -- either price had already
  run through it, or the venue refused the resting send. Folding the two
  together would have made the journal print "Block Broken" for a setup whose
  block was never touched, which is a false statement about the pattern rather
  than a shortcut in the code.

  So ENUM_VETO_REASON gains VETO_LIMIT_MISSED, appended (never inserted --
  enum values are persisted and compared), with rows in:
    * VetoReasonString()               -> "LIMIT-MISSED"
    * the journal cancelReason chain   -> "Limit Entry Missed (price through
                                            entry)"
  VETO_CORRELATION also gains its missing VetoReasonString row ("CORRELATION"):
  it had been falling through to the "NONE" default since v5.26, so every
  consensus veto printed as un-vetoed in the block log.

WHAT A MISSED ENTRY NOW DOES

  Both non-resting outcomes journal the setup's OWN session (save/restore, so a
  live basket keeps the journal), latch the block vetoed with
  VETO_LIMIT_MISSED, stamp deleteOnBarTime, and return false. No order send
  follows. The distinction is preserved in the operator-facing text:

    price through the entry -> "Limit Entry Missed: price already through <px>"
    venue refused the send  -> "Broker Refused Limit Order: <reason> (Code: n)"

THE JOURNAL NOW HAS ONE EXECUTION MODE

  COttoJournal::LogSetupArmed() took a `physical` bool and printed
  "PHYSICAL (Broker Limit Order)" or "VIRTUAL (In-Memory Arm)". With one route
  left the parameter is dead weight, so it is removed and the mode is a
  constant. The journal's Logic label, the session id minting, the one-email-
  per-trade rule and the arm-is-silent rule (v5.42) are all untouched.

OPERATOR NOTES

  * BROKER-REFUSED LIMIT = NO POSITION. That is the intended trade-off. A
    refusal is a venue statement that this order cannot sit there; the previous
    behaviour turned it into a market entry at whatever price the next tick
    offered. Anyone relying on the EA to "always get in" must stop.

  * STALE GLOBAL VARIABLES. v5.37..v5.71 release builds published
    "OTTO_V_ARM_<sym>_<serial>" into the terminal's GlobalVariable store.
    Nothing reads those names any more, so they cannot suppress a setup, but
    they will linger until deleted. A one-time F3 -> Global Variables cleanup is
    the only action needed. A delete-on-init sweep was considered and rejected:
    reinstating the naming convention in order to delete it would have kept the
    convention alive for no behavioural gain.

WHAT DOES NOT MOVE

  Entry price (CalcEntryPrice), stop distance (CalcSLDistance), the far-edge
  target anchor, the Front-Run veto and its anchor, the break veto on the
  physical far edge, the pyramid ladder, the unified one-way ratchet, sizing,
  the High Table auditor, the journal session ownership rules, and the fill
  scanner's SAR / redundant-fill / adoption logic. The virtual fire had no
  behaviour the physical fill path lacks: SAR reversal, redundant-fill close,
  block retirement, basket seeding and the session hand-off all live in
  CheckPendingOrderFills() and SeedActiveTradeFromBlock().
