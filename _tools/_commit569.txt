569: fix — true deep front-edge geometry: entry to the OPPOSITE side of the zone, break veto decoupled

RATIONALE

  v5.66 shipped two changes that each looked coherent in isolation and were
  incoherent together. This release corrects both signs and re-anchors the veto
  that depended on them. It is a REAL trade-character change, not a comment
  sweep: the entry moves from "chase the breakout past the far edge" to "rest a
  limit on the near side and buy the pullback."

  1. THE ENTRY SIGNS WERE INVERTED.

     v5.66 computed gap = 2.0*bh + 1.5*ATR and then added it for a LONG:

         LONG : b.bottom + gap        SHORT: b.top - gap

     b.bottom is the NEAR edge of a RESISTANCE zone and the arming close has
     already gone BELOW it, so b.bottom + gap sits far ABOVE the market. A
     BUY_LIMIT must sit below the ask, so `priceValid = (entryPrice < Bid -
     boundary)` was FALSE on every bar and the broker limit was illegal by
     construction. Every setup was forced onto the virtual stop path, which is
     why the v5.66 "the trigger is a genuine STOP cross" narrative read as
     self-consistent: it was describing the only route the wrong sign allowed.

     The blueprint signs are the coherent ones, and v5.69 ships them:

         LONG : b.bottom - gap        SHORT: b.top + gap

     Near edge pinned at 0.0, far edge at +bh:

         LONG : entry = -(2.0*bh + 1.5*a)    far edge = +bh
         SHORT: entry = +(2.0*bh + 1.5*a)    far edge = -bh

     The entry now sits BELOW the market for a LONG and ABOVE it for a SHORT,
     i.e. on the limit side, so BUY_LIMIT / SELL_LIMIT is legal and the order
     RESTS AT THE BROKER. It fills when price pulls back through the near edge.
     The router needed NO code change: `priceValid` was always correct, it was
     the price handed to it that was wrong. Physical rest becomes the ordinary
     route by construction; the virtual MARKET arm becomes the fallback for a
     tick where price already ran through the entry between the arming close
     and the call.

  2. THE BREAK VETO HAD TO BE DECOUPLED FROM THE ENTRY.

     v5.66 anchored the break test on BlockEntryPrice(). That was only workable
     because the entry sat BEYOND the far edge: the fill and the invalidation
     were the same event, so one anchor served both. With the entry moved to the
     opposite side of the zone the anchor inverts the test's meaning.

     InpArmATR is 0.0, so arming is exactly:
         RESISTANCE: close1 < b.bottom        SUPPORT: close1 > b.top
     while the new entry is a further `gap` past that same edge. An
     entry-anchored threshold for a RESISTANCE LONG is therefore

         close1 > (b.bottom - 2.0*bh - 1.5*a) + ATRBufferBreak*a
               == close1 > b.bottom - 2.0*bh - 1.0*a

     and since arming only requires close1 < b.bottom, the threshold sits
     BELOW the arm trigger. The test is ALREADY TRUE on the arming bar: the
     block arms and vetoes itself VETO_BROKEN in a single pass, and
     CancelOrdersForInvalidBlocks() drops the pending. Every setup dies the
     instant it is armed -- a 100% failure, not an edge case.

     ProcessBlocks() now anchors on the PHYSICAL far edge again:

         double breakLevel = (b.type == BLOCK_SUPPORT) ? b.bottom : b.top;

     Keeping the existing `<` / `>` operators. The two tests now live on
     opposite sides of the zone and can never fire on the same close:

         NEAR edge -> ARM     (RESISTANCE: close1 < b.bottom)
         FAR  edge -> BREAK   (RESISTANCE: close1 > b.top + 0.5*ATR)

     The decoupling is the invariant to preserve. The veto must never move with
     the entry again, which is stated at the anchor site, in the enum banner and
     in the probe.

  3. THE "InpMaxRR MUST STAY ABOVE 3.0" FLOOR IS RETIRED.

     Under v5.66 the target was anchored on the far edge while the entry sat
     bh + 1.5*ATR past it, so the reward carried a (0.5*rr - 1.5) coefficient on
     the ATR term and went NEGATIVE for rr < 3.0. Four comment blocks asserted a
     hard 3.0 floor and the probe pinned it as a configuration invariant.

     With the entry on the near side that term disappears:

         reward = TP - entry = 3*bh + 1.5*a + rr*(bh + 0.5*a)
                             = (3 + rr) * slDist
         risk   = slDist
         realized RR = rr + 3.0      -- EXACTLY, independent of bh and atr

     Verified numerically at 7.0000R for all three shipped geometries
     (1.0/2.0, 2.0/1.0, 0.5/4.0) and 5.0R at rr = 2.0 on a 1e-9-high zone, which
     the old geometry could not survive at all. Because rr > 0 implies
     rr + 3 > 3, the far-edge target can never land behind the entry and the
     floor no longer constrains anything.

     The four blocks that asserted it were REWRITTEN rather than left standing:
     a comment claiming a hard floor that the code no longer has is worse than
     no comment. The shipped 4.0 is now documented as simply the shipped value
     (7.0R), not as a safety floor.

ROLLBACK

  one-line edits with no state coupling: reverting restores the v5.68 breakout

  v5.68's entry signs put the entry on the wrong side of the market, so a
  revert also restores the 100% virtual-route behaviour -- worth knowing before
  rolling back.
