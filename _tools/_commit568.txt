568: feat — comprehensive upgrade of High Table Auditor to monitor deep geometry and stacked risk

RATIONALE

  No trading-logic changes. Every entry, stop, ladder rung, tranche size and
  trail formula is byte-identical to v5.67. What ships here is the WATCHDOG
  catching up to the geometry it is supposed to be watching.

  The recon found four things. Two were already correct, one was a live
  defect, and one was an unmonitored failure mode:

  1. DEEP ENTRY GAP -- ALREADY SYNCED, no change needed.
     COttoBlockManager.mqh:186 and COttoOrderManager.mqh:691/701 already carry
     gap = 2.0*blockHeight + 1.5*ATR in both twins.

  2. STACKED RISK -- ALREADY SYNCED, no change needed.
     nominalStackPct (line 1149) already sums RiskPercent + InpRiskT2Pct +
     InpRiskT3Pct + InpRiskT4Pct = 1.0 + 1.0 + 0.5 + 0.25 = 2.75% nominal,
     4.125% with the 50% tolerance. The deep entry cannot inflate it: both the
     per-leg and the aggregate measure read entry-to-LIVE-STOP distance, and a
     freshly stacked tranche starts at m_basketRRUnit (bh + 0.5*ATR), which is
     1R by construction regardless of how wide the entry gap is. A correctly
     sized scale-in reads at its nominal rung, so the existing body covers the
     pyramid without a new check. Documented in the body rather than churned.

  3. THE TRAILING LADDER -- THIS WAS THE DEFECT.
     AuditTrailingHealth asserted only that the stop had LEFT THE LOSING SIDE
     (`stopRR >= 0.0`) once the trail armed. That invariant is satisfied by a
     stop frozen at +0.01R. A basket that ran to +2.0R -- where the shipped
     ladder owes a +1.0R floor -- and then never ratcheted again read HEALTHY
     FOREVER. m_trailPeakRR was computed correctly and then used ONLY as a gate
     opener, never as an expectation. The watchdog could see the peak and never
     compared anything against it.

     InpTrailStartRR is confirmed to stay 1.0 (OttoDefines.mqh:343-365, pinned
     by the v5.63 probe); the ladder audited is the shipped one:
     +1.0R -> cost-covering BE, +2.0R -> +1.0R, +3.0R -> +2.0R.

  4. A TRANCHE DROPPED BY A PARTIAL STOP PUSH -- WAS INVISIBLE.
     AuditStateConsistency only asked whether the PRIMARY ticket still existed,
     which is a statement about the basket's identity and says nothing about
     whether each leg inside it is protected. COttoOrderManager.mqh:3561-3579
     walks every tranche, sets allApplied = false when a modify is rejected,
     and STILL advances the session ratchet; the one-way guard at 3551 then
     early-returns on every later tick. So a push rejected for only one leg
     leaves that leg at sl == 0 permanently while the EA believes the whole
     basket wears the unified stop.

SOURCE

  CHighTableAuditor.mqh -- ExpectedFloorRR(peakRR, owesFloor)
    NEW private const helper. A conservative LOWER BOUND on the stop the
    milestone ladder must have left in place for an observed peak, resolved
    HIGHEST RUNG FIRST so the strictest earned rung always wins:

        peak >= InpLockProfitRR  -> InpLockProfitTargetRR   (+2.0R)
        peak >= InpLockProfit2RR -> InpLockProfit2TargetRR  (+1.0R)
        peak >= InpBreakEvenRR   -> 0.0R (cost-covering BE)
        otherwise                -> owesFloor = false

    Highest-first matters: at +3.0R the stop already sits at +2.0R, which is
    forward of the +1.0R the next rung would set, so testing the lower rung
    first would UNDER-state the floor and let a lagging stop through.

    Each rung is guarded by BOTH of its inputs, matching the trade manager,
    where a 0.0 trigger OR a 0.0 target disables the rung outright -- so
    disabling a rung here cannot manufacture an expectation the EA never meets.

    Deliberately does NOT re-derive beOffset, the ATR trail value or the
    half-risk rung. Those are the trade manager's private arithmetic and a
    second copy here would drift silently the first time the ATR multiplier or
    the friction model changed -- the second-source-of-truth failure the
    decoupling contract at the top of the file forbids. Because this is a LOWER
    bound, a stop the ATR trail pushed TIGHTER than the milestone floor still
    passes; the check can only fire when the stop is genuinely BEHIND a rung
    its peak already cleared.

  CHighTableAuditor.mqh -- HT_FLOOR_TOLERANCE_R = 0.10
    The ladder is a ONE-WAY ratchet driven from OnTick while this audit runs on
    its own timer, so the tick that pushes price past a rung and the tick that
    writes the wider stop need not share an audit window. The cost-covering BE
    rung also seats a hair ABOVE entry by construction (beOffset carries
    commission + swap + half-spread), so an exact comparison would report a
    correctly-applied BE as lagging. Sized to swallow both and nothing more: it
    is 10x smaller than the 1.0R gap between any two rungs, so a stop that has
    genuinely failed to advance a whole rung cannot hide inside it.

  CHighTableAuditor.mqh -- AuditTrailingHealth
    The losing-side test is inverted into the reporting branch (still the v5.63
    incident, unchanged message and latch), and the healthy path now FALLS
    THROUGH to the floor test instead of returning. New alert
    "HighTable: stop lagging its milestone floor", WARN -- not CRITICAL, because
    the stop has left the losing side and the basket is still protected; what
    is owed is an extra rung of locked profit, not survival. Two-cycle confirmed
    via m_lagFloorSeen, and m_alertSent_LaggingFloor re-arms on every healthy
    exit including the no-floor-owed case. The latch and its confirm flag are
    both reset when the tracked ticket changes, so a sighting cannot confirm
    against a different trade's first cycle.

  CHighTableAuditor.mqh -- CountOrphanLegs() / FirstOrphanLegTicket()
    NEW read-only book queries: magic-scoped legs on this symbol whose
    POSITION_SL is <= 0. The magic scope is deliberate -- an adopted magic-0
    primary is excluded by construction, which is correct, because the adoption
    contract carries the manual leg's own stop, and flagging it would be a
    false positive on every adoption cycle. FirstOrphanLegTicket() exists so the
    alert names a ticket the operator can go straight to.

  CHighTableAuditor.mqh -- AuditStateConsistency
    The orphan sweep runs BEFORE and independently of the phantom branches. The
    two findings are orthogonal (a live primary with an orphaned tranche, or a
    phantom primary with no orphan at all), and folding this behind the phantom
    early-return would re-create the same blind spot one level down. Its own
    latch (m_alertSent_OrphanLeg) and its own two-cycle confirm (m_orphanSeen),
    WARN severity, re-arming through the else-shape the aggregate-risk leg
    already uses.

  CHighTableAuditor.mqh -- AuditRiskExposure doc only
    Records that the 2.75% / 4.125% stacked budget ALREADY covers the deep
    geometry and the pyramiding tranches, and why the deep gap cannot inflate
    the measure. No code change: the recon found nothing to fix.
